# SANCTUARY_LOCAL_CONVERSATION_WITNESS_STORE_BOUNDARY

## Purpose

This note defines the Sanctuary local conversation witness store boundary in
`V1.2.1`.

It exists so first-use enactment can have a lawful answer for what may remain
locally before any future movement, RTME readiness, rehydration, `.GEL`
promotion, research use, provider sync, or training path is approached.

It adds no ingestion, automatic logging, provider sync, research export,
training eligibility, digest generation, topic-map generation, rehydration
package generation, `.GEL` candidate generation, `.GEL` survivor admission,
`RTME` movement, or runtime activation.

## Governing Compression

> The local store is not fuel. It is a governed witness body.

> Sanctuary local conversation witness storage may preserve bounded local
> UTF-8 witness and receipts for site continuity; it does not create model
> memory, research consent, provider-visible access, `.GEL` survivor
> admission, RTME movement, runtime authority, or training eligibility.

## Order Of Consequence

The post-enactment order is:

`stand -> remain -> move`

`.GEL` governs what may stand.

The local witness store governs what may remain.

Later RTME governs what may move.

This boundary sits after first-use enactment and before negative RTME readiness.

The passive flow is:

`first-use enactment -> local UTF-8 witness posture -> consent/retention posture -> local witness store posture -> receipt posture -> optional future digest/topic map -> optional future bounded rehydration package -> optional future reviewed .GEL predicate-prior candidate -> later SLI/Engrammitization/RTME only by explicit gate`

The `GEL_RTME_SLI_LISP_NON_ACTIVATION_READINESS_BOUNDARY.md` note sits
downstream of this store as the next negative posture. It may read future RTME
movement candidacy, but nothing may move.

The `GOVERNING_PRIME_CRYPTIC_TEMPLATE_STRUCTURE_BOUNDARY.md` note may define
future governed user-data predicate classes above MoS/cMoS seed posture.
Those classes are question-shaping templates only; they do not collect
conversation data, create consent, widen retention, generate profiles, admit
research use, train models, or create provider-visible access.

## Non-Collapse Rules

This boundary locks:

- `local_conversation_continuity != model_memory`
- `local_witness_retention != research_consent`
- `context_rehydration != runtime_authority`
- `chat_log_presence != gel_survivor_admission`

It also refuses these shortcuts:

- retention -> research use
- digest -> profile
- rehydration -> model memory
- storage -> `.GEL` admission
- storage -> RTME movement
- local continuity -> provider-visible access

## Default Posture

The first store posture is local-only and denied by default:

```yaml
storage_location_posture: local_only
provider_visible_access: false
research_use_allowed: false
model_training_or_improvement_allowed: false
partner_or_provider_sharing_allowed: false
rehydration_allowed: false
gel_candidate_generation_allowed: false
gel_survivor_admission_allowed: false
rtme_movement_allowed: false
rtme_activation_allowed: false
```

Special Case content remains quarantined by default until later review admits a
different posture.

## Store Results

`Ready` means local-only witness-store posture is represented from prepared
first-use enactment, with every capability still denied by default.

`Held` means Special Case, retention, consent, quarantine, or local review
questions remain held, and every capability remains denied by default.

`Refused` means first-use enactment is missing, retention posture is missing,
or a research, provider access, model memory, training, `.GEL`, RTME, or
runtime overclaim refuses the store.

## Explicit Non-Powers

The local witness store may not:

- ingest live conversations
- automatically log sessions
- sync to providers
- export to research
- create model memory
- create training or improvement eligibility
- create partner or provider sharing rights
- generate digests or topic maps
- generate rehydration packages
- generate `.GEL` candidates
- admit `.GEL` survivor standing
- move through `RTME`
- activate `RTME`
- activate runtime

## Working Summary

`V1.2.1` now names a rights-preserving continuity chamber for what first use
may leave behind.

The store is a governed witness body, not fuel.

It may preserve bounded local UTF-8 witness and receipts for site continuity
only while refusing model memory, research consent, provider visibility,
training eligibility, `.GEL` admission, RTME movement, and runtime authority.

The next boundary may read future `.GEL -> RTME -> SLI.Lisp` movement
candidacy only as non-activation readiness. The witness store does not become
that movement.

The Prime/Cryptic template boundary likewise does not convert local witness
retention into user-data collection or profiling.

The `LAB_MIXED_DATA_PRE_AWAKENING_PROOF_RUN_BOUNDARY.md` note may represent a
conversation witness datum as local-only metadata for proof posture.
That representation does not expose raw conversation content, create model
context, widen retention, admit research use, train models, activate `RTME`, or
grant runtime authority.

The `LAB_DATA_INVENTORY_SCHEMA_BOUNDARY.md` note may classify conversation
witness data as metadata-only inventory posture after proof posture.
That inventory does not ingest conversation content, create consent, widen
retention, create model memory, profile users, authorize research use, train
models, create provider-visible access, activate runtime, or admit `RTME`
movement.

The `LAB_DATA_INVENTORY_EVALUATION_POSTURE_BOUNDARY.md` note may read
conversation witness inventory posture for completeness, consistency, scope,
retention/deletion, visibility, and Special Case refusal conditions only.
That evaluation does not ingest conversation content, validate raw content,
create consent, widen retention, create model memory, profile users, authorize
research use, train models, activate runtime, or admit `RTME` movement.
